## Goals / Non-Goals

**Goals:**

- 卡组编辑按完整编辑手势记录独立的本地内容历史，精确恢复卡牌数量、分区和排列。
- 用同一套对战有效历史语义驱动单人模式和双人宿主，避免各对战模式对“一步”的理解不同。
- 在确定的输入边界重建候选对局，校验后再切换；原会话在恢复提交完成前保持可保留。
- 将决斗、玩家视角、AI 和网络在途操作纳入恢复边界。
- 同目录增量安装，固定资源根目录，并让原版与新版的程序和可写配置并存。

**Non-Goals:**

- 不逐卡编写反向效果脚本，不修改原卡片脚本来实现撤回。
- 不对现有可执行文件做注入、内存补丁或整进程快照恢复。
- 不承诺改变操作路线后仍产生与旧路线相同的所有随机结果；保证相同历史确定性和正确恢复随机状态。
- 不在这次提案生成阶段下载源码、编译、修改安装包或向 GitHub 发布。

## Decisions

### 1. 用户已确认的要求与首版默认值

已确认：四种对战场景；回到发起者最近一次提交选择之前并连带撤销后续双方操作；连续撤回；朋友局逐次同意；独立程序同目录运行并直接共用资源。用户随后新增卡组编辑页面撤回加入/删除卡牌的要求，并关心保留原编辑器及不检查、不洗切开局选项。

为形成可执行计划，采用以下首版默认值，作为设计选择而非额外的用户原话：对战撤回限当前未结束的双人对局；编辑撤回限当前普通编辑会话并支持连续撤回；本地双开自由撤回需显式选择仅本机房间；朋友确认超时为 30 秒且视为取消；暂不提供重做、跨局回退、赛后恢复或对战间换备页面撤回。撤回是否支持的判断覆盖整场对局，不能静默将 AI 模式降级为不支持。

### 2. 从可复现的源码基线开始

开发源码放在与运行资源分开的源码工作区。使用修改后的完整源码或固定提交的子模块保存客户端、内核和 WindBot；构建清单固定上游地址、提交、依赖、架构和编译器版本。上文的 master 链接仅供定位，不能直接作为发布基线。

先读取本地程序版本和校验值，追溯匹配的发布来源；对选定源码做无撤回改动的 Windows 构建，并使用当前数据库、脚本、扩展与 AI 列表验证单人模式、建房、双开和 AI。如果不能证明兼容，明确记录缺失依据或失败案例，修订基线后再推进，不能要求用户复制或替换整套原资源来掩盖问题。

选择源码构建是因为要修改对局宿主、网络消息及 AI。仅附加 Lua 脚本不能承担这些改动；二进制补丁则难以保持跨版本可追溯性。

### 3. 记录完整历史，以玩家确认的选择建立撤回点

历史由对局宿主维护；单人模式使用同样的会话逻辑。保留如下信息：

| 记录 | 内容 |
| --- | --- |
| 初始会话 | 引擎/资源清单、随机种子或种子序列、规则（含不检查/不洗切设置）、先后手、双方初始牌组顺序，或单人场景脚本及参数。 |
| 有效响应 | 顺序号、玩家、请求类型与规范化输入摘要、响应字节、人工/自动来源、关联消息进度。 |
| 撤回点 | 人工有效响应的索引、提交之前的待输入提示、玩家、目标说明、计时状态及校验摘要。 |
| 外部会话状态 | 客户端各自可见的消息历史、宿主计时与等待对象、AI 恢复日志、历史版本。 |

所有影响决斗的响应都必须记录；只有人工确认并被引擎接受的游戏选择才是该玩家的撤回目标。UI 层标注来源，宿主验证当前待输入对象并在引擎接受后将记录提交；`MSG_RETRY` 对应的无效尝试不保留为有效历史。自动跳过时点需要重放，但不增加玩家连续撤回时的空步骤。

批准后，若目标响应索引为 k，则重建到提交 k 之前，仅保留此前的有效历史。截断发生在恢复成功提交时；失败不改变原历史。恢复后的新响应形成新分支，并重新记录录像。目标摘要按查看者权限生成，不能在对方确认弹窗中泄露未公开卡片名称。

### 4. 使用初始条件与历史响应重建候选决斗

为当前对局创建独立候选会话，使用相同资源版本和初始随机条件，从起点快速执行保留历史。到目标选择提示时停止，比较待输入玩家、请求内容、历史消息摘要以及可查询的规范化决斗状态；候选重建不触发真实网络发送、UI 动画、音效、文件写入或重复聊天。

这条路线复用录像的确定性基础，同时不进入会公开双方面板信息的录像 UI。实现时需按决斗句柄隔离读取/日志回调和缓存使用，防止重放通过全局回调改变原会话。若匹配源码不能安全共存两个内核会话，必须在前置验证中解决隔离方式并更新设计，不能先销毁原会话来简化恢复。

替代方案是完整内核快照和逐动作反向撤销：前者涉及 Lua 运行状态、对象引用及效果队列的保存恢复，所查接口未提供此能力；后者需要覆盖所有卡片效果，难以保证完整性。因此首版选择重建，并用恢复耗时记录判断未来是否需要缓存检查点。

原卡组编辑器及 AI/普通建房页面的开局选项保留。重建读取该局已保存的规则和初始牌序，保留匹配原版的不洗切标志及语义，不重新调用开局随机洗牌；不检查选项只沿用原基线的校验范围，不扩大为接受格式错误数据。

开局固定数据库及实际可执行脚本资源的内容视图；资源可以直接读取原目录，并在内存缓存/固定读取内容，不复制持久化资源目录。对局内资源变化不能混入重建：使用该局固定内容；若无法保持则拒绝回退并保留原局。图片和音效不参与决斗兼容清单。

### 5. 朋友联机采用宿主协调的恢复事务

新增协议握手确认撤回能力和决斗资源清单。撤回版房间只在检查通过后开始；保持原版可执行文件与其房间行为不变。协议扩展的实际编号应在匹配源码上分配，避免与现有消息冲突。

对局消息、出牌响应与撤回消息关联会话 ID 和单调递增的历史版本；请求还包含请求 ID、目标索引与摘要。每个会话只允许一个撤回事务，重复消息幂等，旧版本输入不能进入新决斗。

```text
RUNNING --> WAIT_BOUNDARY --> CONSENT --> PREPARE --> COMMIT --> RUNNING
                                  |          |          |
                                  v          v          v
                               CANCEL     ABORT     PAUSED_FAILED
```

- `WAIT_BOUNDARY`：效果处理期间排队，在安全输入边界固定目标及版本。已结束则取消；直接可处理时跳过等待。
- `CONSENT`：冻结出牌及决斗计时，展示具体目标，等待另一名玩家对该请求的同意。拒绝或 30 秒超时恢复原提示与冻结前时间。本机自由撤回及单机/AI 跳过此状态。
- `PREPARE`：保留原会话，重建候选内核和 AI。按各玩家视角准备恢复数据；客户端构建候选显示状态，确认消息完整性、目标提示与版本后返回就绪。
- `COMMIT`：宿主切换候选并递增历史版本，发送提交通知；双方确认相同版本后再解除冻结。成功后计时采用目标撤回点的剩余时间，录像仅保留新分支。
- `ABORT`：提交前失败，废弃候选；连接正常时双方恢复原局继续。丢失响应可按请求 ID 重传，不新增事务。
- `PAUSED_FAILED`：提交期间无法确定某方是否已切换时保持暂停，显示同步失败。只有确认全员同一版本才恢复；首版不承诺断线重连恢复，允许退出重开，不能让一方单独继续或静默退回另一版本。

客户端恢复数据采用逐玩家过滤后的起始状态和必要事件/提示重放，构建完整的候选界面模型。不能只发送场上卡片列表，也不能把宿主全量日志、含双方牌组的原始录像或全状态哈希发送给普通客户端。历史中已经看到的信息无法从人的记忆消除，但目标点界面重新遵守其可见性。

本机自由撤回房间显式绑定回环接口，仅供本机双开；普通局域网房间始终走 `CONSENT`。不通过昵称或客户端自报“同机”来切换策略。

### 6. WindBot 通过确定性重放恢复决策上下文

适配版 WindBot 加入受控的会话初始化、消息调度及可复现随机源。AI 日志记录初始配置/牌组执行器、随机种子与影响决策的外部输入、AI 可见消息的顺序、所有决策回调和产生的响应。时间等外部值若影响决策，也必须受控或记录。

恢复时启动候选 AI 会话，从同样的初始化状态重放此前的消息与决策回调，抑制真实发送和聊天，并逐次比对原历史的输入与输出。不能只把旧响应喂给决斗内核：那不会重建执行器字段、选择队列、随机消耗和决策记忆。候选 AI 到达与目标点对应的日志边界并通过校验后，才随宿主提交切换；旧 AI 在此之前保持暂停并保留。

优先采用会话重建，避免首版手写序列化所有牌组执行器的私有字段。固定消息/决策顺序和随机状态是这一路线的前提，需要覆盖实际安装包 AI 列表中的执行器。若存在无法控制的状态或重放不一致，作为 AI 支持的发布阻断问题处理，不能将“刷新 AI 牌面”作为替代实现。

### 7. 同目录资源共用，新增文件按名称隔离

客户端启动时取自身可执行文件目录为资源根；所有资源访问均从该根解析，保留原有扩展和包加载优先级。启动 AI 时传递明确资源路径和受控工作目录，适配 AI 直接读取原 `WindBot/Decks`、`Dialogs`、`bots.json` 以及同一数据库/扩展数据视图。

计划安装布局如下；新增依赖必须逐项列入发行清单，按名称隔离或放入专用子目录，不能替换原 WindBot 的共享依赖。

```text
ygopro/
  ygopro.exe
  ygopro-undo.exe                (new)
  system.conf
  system-undo.conf               (generated)
  pics/ deck/ script/ expansions/ pack/
  cards.cdb
  WindBot/
    WindBot.exe
    WindBot-undo.exe             (new)
    WindBot-undo.exe.config      (new)
    Decks/ Dialogs/ bots.json
  undo-mod/                     (new dependencies and documentation)
```

首次读取原版兼容设置作为默认值，此后只保存新版配置；配置写入使用进程间协调及原子替换，避免双开写坏文件。会话历史和日志使用独立会话标识；共享卡组文件只在玩家主动保存时更新；卡组编辑撤回仅改变当前内存内容，对战撤回和安装过程不改动原卡组文件。

### 8. 源码仓库与发行包分别管理

源码工作区提交修改后的客户端与 AI 源码、固定依赖信息、构建打包脚本、配置模板和这些 OpenSpec 文档。Git 忽略构建输出、运行目录、个人配置及资源库；不在当前整个游戏安装目录直接执行全量 `git add`。

Release ZIP 只包含新增程序、必要依赖、配置模板、安装说明和许可/来源信息。默认配置由程序首次生成，不打包开发者的 `system-undo.conf`。每个包关联源码标签和构建清单，说明适用的原版版本、运行环境和朋友需安装的兼容版本；源码下载包不充当玩家安装包。

最初提案阶段只创建规划文件，后续发布流程使用实际仓库和版本，不预设 GitHub 账号、仓库地址或执行任何发布动作。

### 9. 卡组编辑使用本地内容快照历史

卡组编辑记录主卡组、额外卡组和副卡组的有序卡片 ID 序列，保留重复卡及其排列；历史只在当前编辑会话内存中存在，不使用决斗重建、网络批准或 AI 恢复。卡组内容较小，首版选择按操作保存内容快照，避免为同名卡、跨区移动和位置恢复逐一维护反向命令。这里的快照是卡组数据副本，不是内核或进程存档。

以完整用户操作为事务边界：操作开始前保存三个分区；合法完成且内容实际变化后，将操作前快照推入历史；撤回时恢复栈顶快照并弹出该记录。快照恢复不重复触发增删历史，不通过当前加卡限额过滤而丢掉原有内容，并刷新数量、悬停和选中状态。用户在撤回后继续编辑时只追加新操作，不提供重做。

必须在上层手势和命令边界记录，不能简单给每个 push/pop 加一条历史：现有拖拽在移动开始就暂时移除卡牌，落下时才尝试放入。记录从实际移除之前开始，到释放/取消结束；失败或取消时恢复操作前的完整顺序，不把临时移除或回插算作独立操作，拖拽期间禁用编辑撤回。

用户明确要求的是卡牌增删撤回。为保持历史连续，首版设计默认把跨区拖动、排序、洗牌和清空当前卡组内容也作为各自的一步内容编辑；搜索、筛选和查看卡图不生成历史。删除卡组文件、文件管理操作、对战间换备页面不属于本次编辑撤回范围。

UI 增加撤回按钮和 Ctrl+Z。焦点位于文本框时将快捷键留给文本控件；有阻塞弹窗、只读状态或正在拖拽时不执行卡组内容撤回。卡组名输入变化不是卡牌增删，不改变卡组历史。

每个编辑会话维护最近一次成功保存的内容快照：普通保存只更新该基准，不清空历史；保存后再撤回依据当前内容与基准的比较计算未保存标记。保存失败不改变基准。只有主动保存才更新原 .ydk 文件；成功加载其他卡组、重新加载、新建、另存为新的卡组或退出时清空旧历史。不同进程、不同卡组和对战会话不共享撤回栈。

这部分仅依赖源码与编辑器基线，可在对战/AI 重建验证之外独立实施和验收。发行前仍需同时满足编辑和四种对战模式的规格，不以编辑撤回完成代表对战撤回完成。

## Risks / Trade-offs

- [低层增删被误计为多个步骤] -> 在完整编辑手势边界记录三个分区快照，覆盖拖拽成功、失败和取消路径。
- [编辑历史串到另一副卡组或错误改写文件] -> 历史按编辑会话隔离，切换时清空；保存基准单独维护，只由显式保存写文件。
- [本地二进制无法对应确切源码] -> 先追溯发布来源并完成无功能改动的兼容构建；版本号本身不足以证明兼容。
- [资源或随机条件导致重放分歧] -> 固定单局资源视图、记录所有输入、逐步比较提示与输出；失败保留原会话。
- [长对局重建耗时] -> 无动画重放、显示恢复状态，记录短局和长局耗时与内存；首版不承诺未经测量的毫秒级响应，不静默截短有效历史。
- [AI 状态不能确定性重建] -> 独立验证随机源、决策副作用和实际牌组执行器；作为全功能发行的阻断条件。
- [网络旧消息或提交结果不明确] -> 会话/历史版本校验、幂等请求、双端就绪与提交确认；不确定时暂停。
- [恢复数据泄露对手信息] -> 复用并验证逐玩家过滤，客户端只接收自身可见恢复流，弹窗使用可公开的目标摘要。
- [回调及重放副作用改变原局] -> 验证并隔离候选会话的引擎回调、AI 输出、计时、UI 与文件操作。
- [同目录的新依赖干扰原版] -> 新程序独立命名，依赖采用清单与隔离目录；安装前后核对原文件并做原版启动回归。

## Migration Plan

1. 固定源码和构建环境，完成对当前资源包、卡组编辑器及两个开局选项的基线兼容验证；卡组编辑撤回可在此后独立实施。
2. 通过决斗与 AI 重建前置验证，再实现历史、单人入口、宿主事务、客户端同步和 AI 适配。
3. 将产物部署到现有目录的新增路径，验收卡组编辑撤回、四种对战模式、错误场景、开局选项及原版并存；不复制共享资源。
4. 在源码仓库记录验证结果，打标签并生成与之对应的增量 ZIP；实际 GitHub 发布在后续明确的发布任务中执行。
5. 卸载按发行清单仅移除新增程序、专用依赖和可选新版配置/日志；原安装资源和原程序继续可用，不递归清理共享目录。


实现范围补充（2026-09-10）：当前撤回房间只接受两名玩家的单局（Single）。Match 三局两胜的跨局与换备生命周期、Tag、观战暂不开放，菜单/协议均明确拒绝；四种已要求的使用场景仍保留。该限制是依据现有两人恢复参与者模型作出的首版实现决定，不将未完成的模式静默伪装成支持。两台设备局域网与人工视觉验收仍需用户后续配合，用户已确认有第二台 Windows 电脑。
