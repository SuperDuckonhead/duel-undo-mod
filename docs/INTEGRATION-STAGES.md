# 原生流程优先的集成阶段

用户最新架构约束：保留原客户端菜单、鼠标事件分发和正常对战流程。新增逻辑主要负责记录内核实际接受的响应、在独立候选会话中恢复历史，以及双方恢复事务的同步。应复用已经实现的编辑、单机、AI 和联机能力；分阶段验证不等于删除或缩减用户已授权的功能。

## 实现边界

- 原菜单仍负责选卡组、开局设置、猜拳、先后手、正常操作及结束对局；普通鼠标事件继续经过原生 GUI 分发，不以测试合成的按钮事件替代用户操作。
- 记录层只在内核接受响应后追加有效历史，保留 Manual、Automatic 和 Bot 来源；未提交选择和 MSG_RETRY 拒绝的响应不能成为新的撤回点。
- 恢复层固定初始条件和资源，重建并验证候选内核、界面及 AI，提交前保留原局；同步层负责冻结、就绪、提交、确认、恢复输入和失败处理。
- 输入门应表达明确的状态与边界，不能因为“尚无可提交的决斗响应”而吞掉菜单、猜拳或正常确认所需的原生事件。恢复事务也不能让旧点击作用于新的提示或另一笔协商。

## 阶段与通过条件

| 阶段 | 验证重点 | 进入下一阶段前的证据 |
| --- | --- | --- |
| 1．正常原生流程 | 原菜单开局，真实鼠标猜拳与先后手，正常对战和结束，以及需要用户操作的阻塞确认 | 实际窗口的原始输入经原生分发到控件；使用真实主循环、帧等待和确认信号，能正常继续与退出。覆盖默认设置及此前强制设置未经过的分支。 |
| 2．单机与编辑撤回 | 编辑增删、保存与历史隔离；单机有效选择、连续撤回和新分支 | 原生操作保持可用；恢复成功后目标提示可操作，失败后原提示可继续；编辑历史与对战历史不混用。 |
| 3．AI 对战 | 原菜单启动真实 AI，真人与 AI 回合、候选 AI 重放及撤回后继续 | 同时验证原生交互与实际 AI 上下文恢复；默认猜拳、平局、AI 获胜后的先后手流程不能由固定 Hand 测试替代。 |
| 4．双人同步 | 先验证本机双开，再验证两台设备 LAN | 本机自由撤回与逐次同意按各自策略执行；真实同意/拒绝、完整提交屏障、失败保留或统一暂停均有证据。两设备结果不能由同机 TCP 测试代替。 |

这些阶段是集成验收顺序。已有模块、确定性重放、故障注入及实际进程测试仍保留并复用；原生交互修复后，应针对受影响的路径回归，而不是把已有功能当作尚未实现重新开发。

## 当前状态与未闭合项

当前已修复正常开局时的原生输入、撤回后菜单/卡牌列表的控件绑定、终局录像命名/保存/取消及随后确认，并加入对局 Ctrl+Z；这些局部修正不代表所有暂停与确认路径已经通过。以下事项是本轮明确识别、仍需单独闭合的项目：

- Consent 同意/拒绝按钮的真实鼠标操作，以及按下与抬起跨协商结束或新事务时的身份绑定。
- MSG_RETRY 后的原生提示、确认和重新提交。
- HINT_MESSAGE 与 CONFIRM_CARDS 的原生阻塞确认、帧等待及后续正常流程。

过去直接调用 `OnEvent(EGET_BUTTON_CLICKED)` 的测试可证明对应处理函数行为，但绕过了真实鼠标到 GUI 的分发；使用 `SetNoWait(true)` 的测试也未验证实际等待与解除等待。这些证据不能单独作为原生交互验收通过依据。

每阶段应记录所用源码/产物、入口设置、真实操作、结果和限制。未完成的真实交互、两设备 LAN、性能与最终候选验收继续保持开放；本页不声明全部功能或发行验收已经完成。
终局保存原生回归见 tests/replay-save-ui.md：实际鼠标和键盘保存/取消/改名、自动保存、最后确认及正常返回菜单均通过；不代表上面对局中阻塞确认已完成。
