# YGOPro 撤回 Mod 总实施计划 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将已确认的设计拆成 21 个可单独验证和提交的实现任务，交付卡组编辑撤回及四种对战模式的撤回版客户端。

**Architecture:** 卡组编辑使用本地内容快照；对战使用初始条件与有效响应历史重建候选内核，AI 重放真实决策回调，联机经逐次同意和双方提交确认。各子计划有自己的测试交付物，最终由同目录安装与发行验收汇合。

**Tech Stack:** Windows、固定版本 YGOPro C++/ocgcore/Lua、Irrlicht、WindBot .NET Framework 4.8、Premake/MSBuild、CMake/CTest、PowerShell、Git。

**Spec:** [proposal](../../../openspec/changes/duel-undo-mod/proposal.md)、[design](../../../openspec/changes/duel-undo-mod/design.md)、[17 条需求 / 43 个场景](../../../openspec/changes/duel-undo-mod/specs/duel-undo/spec.md)、[47 项 OpenSpec 任务](../../../openspec/changes/duel-undo-mod/tasks.md)。

## Global Constraints

- 用户已确认设计；本轮仅拆解计划，不下载源码、不编译、不改客户端、不向 GitHub 发布。
- 当前安装根 F:/MyCardLibrary/ygopro；计划执行时在其 dev/duel-undo-mod 建独立开发 Git 根，运行资源不进入源码仓库。
- 新程序名称 ygopro-undo.exe、WindBot/WindBot-undo.exe；新版配置 system-undo.conf；原程序、配置及共享依赖不覆盖。
- 直接共用 pics、deck、script、expansions、pack、cards.cdb、字体/声音/纹理，以及原 WindBot 数据；不复制资源库。
- 编辑撤回支持三个分区、重复卡与顺序；完整手势一步；按钮/Ctrl+Z；只改内存，主动保存才写 .ydk。
- 对战回到发起者最近一次有效人工选择之前，撤销其后双方/AI 行为，支持连续撤回和新分支。
- 单人练习、AI、本机双开、朋友 LAN 均在交付范围；朋友每次明确同意，超时 30 秒。
- 候选失败保留原局；提交不明保持暂停；客户端只接收自身可见信息；AI 必须恢复决策上下文。
- 保留编辑入口和 AI/普通建房的不检查/不洗切设置，撤回不额外洗牌。
- 无重做、跨局、赛后恢复、TAG、换备编辑撤回和断线重连承诺。
- 源码 SHA、协议外层编号、编译器/依赖精确版本必须从实际证据确定，不在计划中虚构。

## 使用方法与当前边界

先阅读规格与对应子计划，然后按任务中的失败测试、最小实现、同一测试通过、提交顺序执行。每个勾选步骤是一个操作；完整 UI/内核接入可能由多个这样的操作组成，不能把一组开发工作误报为已用单次检查完成。外部源码获取、构建和两设备验收不承诺 2–5 分钟完成。

计划中的新模块接口是拟采用的代码合同；现有接入文件来自查阅的上游参考，B1/B2 会在锁定提交后复核实际签名和构建文件。源码尚未取得，因此不提供虚构行号、不宣称代码片段已编译。若接入映射不一致，先修正相应任务的文件/签名/测试命令，再实施；已确认行为保持不变。

采用完整源码导入的独立开发根，避免为了公开修改要求提前创建多个远程 fork。开工时先执行 using-git-worktrees 的隔离检查：当前没有 Git 仓库，先建立上述独立开发根；已有源码仓库时使用其隔离工作树。只对开发 Git 根执行明确路径的 git add，不对安装根执行全量添加。

## 两个前置验收

**Gate-A：源码与原资源兼容。** 有真实来源/固定提交证据、成功 Windows 构建，原卡组编辑/单人/AI/双开与两个开局选项均能使用当前资源。无法证明精确对应时诚实记录兼容基线差异；不能只引用“1.036.2”。

**Gate-B：内核与 AI 重建可行。** 固定资源/种子/有效输入得到同一目标和后续行为，两个内核会话不串状态；候选 AI 通过真实决策回调和随机序列校验，重建不对原局发包或写文件。失败先解决具体反例，不靠提前销毁原局或删除 AI 范围继续。

## 执行与验收约定

- 每个任务先得到明确的行为失败，再实施对应代码，重跑同一测试；基础搭建可用缺文件/命令失败作为首个证据，不能把环境缺失当成业务测试通过。
- 新 CMake 测试目标添加后先重新配置，再构建、CTest；真实客户端/内核/AI 用 B2 锁定的构建命令。
- 代码片段只展示该步骤的接口/核心逻辑，集成必须执行该步骤列出的真实 UI、内核或双端验收；不能只复制片段就打勾。
- 每个任务单独提交明确文件，记录测试证据；实际编译/测试/集成失败时保持未完成。
- 不要求在规划阶段虚构时间预估；Gate-B 后按真实重建速度与源码改动范围更新估时。
- 两设备 LAN 缺设备、AI 列表有失败、原资源兼容未通过时保留未完成，不能标记可发行。
- R3 产出本地包与具体可审查发行材料；GitHub 发布由后续明确发布任务执行。
